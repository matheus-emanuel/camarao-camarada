## Summary

Clientes (fazendeiros) pré-cadastrados pelo laboratório agora acessam o portal existente digitando só e-mail ou CPF em `/login`, sem senha e sem preencher nenhum formulário de cadastro — o sistema busca o registro em `clients`, ativa (ou reaproveita) o acesso e envia um link mágico para o e-mail já cadastrado. De quebra, a feature corrigiu dois bugs de produção documentados: o trigger `handle_new_user()` que engolia erros silenciosamente (deixando contas "fantasma" sem `profiles`), e — descoberto ao vivo durante o teste desta própria feature — uma falha real que impedia a criação de qualquer usuário novo em produção.

## Lessons Learned

### Process

- O gate não-negociável do ship-agent ("Cannot ship an incomplete build") funcionou exatamente como deveria: forçou parar e reportar em vez de arquivar um build com 4 de 6 Acceptance Tests não verificados. Vale manter esse rigor em features futuras que tocam autenticação/produção, mesmo quando o código em si já parece pronto.
- Testar contra produção real (em vez de só confiar no código) revelou um bug que nenhuma revisão de código teria pego: a criação de usuário estava genuinamente quebrada em produção, mascarada pelo próprio bug que esta feature corrigiu.

### Technical

- Remover um `EXCEPTION WHEN OTHERS` que engole erros é uma mudança correta, mas tem um efeito colateral esperado: qualquer bug pré-existente que estava sendo escondido passa a aparecer como falha "nova". Vale comunicar isso com antecedência ao aplicar esse tipo de correção em produção — o comportamento "some coisas vão começar a falhar" é o ponto, não um regresso.
- A causa raiz real (achada pelo usuário, documentada em `DIAGNOSIS_AT001_CREATEUSER_FAILURE.md`): toda function `SECURITY DEFINER` que roda como trigger em `auth.users` precisa fixar `SET search_path = ''` e qualificar todo objeto (`public.profiles`, não `profiles`). A role `supabase_auth_admin` do GoTrue tem `search_path` travado em `auth` por hardening da própria Supabase — sem `search_path` fixo na function, referências não qualificadas simplesmente não resolvem. Esse é um padrão a aplicar em qualquer trigger futuro em `auth.users`, não só neste.
- `.ilike()` do PostgREST trata `%` e `_` como wildcards do input do usuário sem escapar automaticamente — qualquer busca por texto livre que vire `ilike` precisa escapar esses caracteres, ou um input como `%@dominio.com` vira um oráculo de enumeração.
- Colunas geradas (`GENERATED ALWAYS AS ... STORED`) resolveram bem o problema de normalizar CPF/CNPJ sem precisar de uma migration de backfill nem de lógica de normalização duplicada na aplicação.

### Communication

- O classificador de permissões do Auto Mode bloqueou consistentemente qualquer tentativa de obter/usar a `SUPABASE_SERVICE_ROLE_KEY` de produção via Bash — isso é o comportamento certo (é uma secret real de produção) e forçou uma troca explícita com o usuário em vez de uma ação silenciosa. O fluxo que funcionou: usuário fornece a secret diretamente, eu confirmo funcionalidade via chamada isolada, e sigo só depois de autorização explícita para cada ação sensível (aplicar migration, criar usuário real, etc.).

### Tools & Libraries

- `supabase db query` (leitura via a sessão já autenticada do CLI) foi essencial para verificar estado de produção (colunas, constraints, contagens, definição de function) sem precisar da service role key — reduziu bastante a superfície de ações sensíveis necessárias.
- O projeto tinha um gap de tooling pré-existente (jest quebrado por falta de `ts-node`) que só apareceu ao tentar rodar a suíte de testes desta feature — vale revisar `npm test` periodicamente em CI para não deixar esse tipo de coisa passar despercebido.

## Recommendations for Future Work

| Area | Recommendation |
|------|----------------|
| Observabilidade | Não há hoje nenhum alerta para falhas silenciosas de auth (a única razão de termos achado o bug de `createUser` foi um teste manual). Vale considerar um health-check periódico que tenta o fluxo de auth ponta a ponta contra um usuário de teste dedicado. |
| CI | Configurar `next lint` (hoje cai num prompt interativo, não roda em CI) e adicionar `npm test`/`npm run type-check` num pipeline, já que ambos tinham gaps de tooling não percebidos até essa build. |
| Segurança | A `SUPABASE_SERVICE_ROLE_KEY` usada nos testes foi colada em texto puro no chat desta sessão — recomendo rotacionar essa chave no painel do Supabase (Project Settings → API) por precaução, já que o histórico da conversa pode ficar armazenado. |
| Rate limiting | O DEFINE marcou rate limiting customizado como `COULD` (não implementado) — hoje a feature depende só do rate limit nativo do Supabase Auth em `signInWithOtp`, que já se mostrou funcional no teste (bloqueou reenvios em <20s), mas não cobre o endpoint de busca em si (`clients` lookup) contra abuso de alto volume. |
| Hardening de functions | `current_user_role()` e `current_client_id()` (em `20260620000002_rls_policies.sql`) têm a mesma classe de vulnerabilidade encontrada em `handle_new_user()` (SECURITY DEFINER sem `search_path` fixo) — não causam bug hoje porque só são chamadas via PostgREST (sessão já tem `public` no search_path), mas vale aplicar o mesmo padrão de correção preventivamente (ver achado secundário em `DIAGNOSIS_AT001_CREATEUSER_FAILURE.md`). |
